Conceito

O que é AntiGravity?

AntiGravity é um pacote Python que nasceu de um Easter Egg famoso da linguagem — import antigravity abre um quadrinho do xkcd sobre Python. Mas aqui usamos o conceito como filosofia de design:

  • Legibilidade primeiro: código que qualquer pessoa consegue ler e entender.
  • Modelos explícitos: escrever a estrutura (classes, atributos, métodos) antes de implementar a lógica.
  • Sem magia escondida: cada decisão de design é documentada e justificada.
  • Iteração visual: usar diagramas como artefato de comunicação entre desenvolvedor e cliente.
Na prática: vamos usar AntiGravity para escrever as classes como esqueletos documentados — só assinaturas e docstrings, sem lógica ainda.

Curiosidade

O Easter Egg do Python

# Cole isso no terminal Python e veja o que acontece: import antigravity

Abre o quadrinho xkcd #353 no navegador — Python te ensina a voar.
Mas além da piada, o import revela a filosofia Python:

  • Legibilidade conta — código é lido muito mais do que escrito.
  • Explícito é melhor que implícito — diga o que o código faz.
  • Simples é melhor que complexo — não complique sem necessidade.
Esses princípios guiam como vamos modelar a Imobiliária R.M: classes simples, explícitas e legíveis.

Engenharia de Prompt

Por que prompt engineering muda tudo

Antes de pedir ao modelo (Claude, GPT, Gemini) que gere código ou UML, você precisa saber exatamente o que quer — e saber comunicar isso com precisão. Prompt ruim = output genérico. Prompt profissional = output aproveitável.

Garbage in, garbage out

O modelo não tem contexto do seu projeto. Se você não der, ele inventa — e inventa coisas plausíveis, mas erradas.

Prompt é especificação

Escrever um bom prompt exige o mesmo raciocínio de escrever um bom requisito de software.

Iteração é parte do processo

Nenhum prompt é perfeito na primeira vez. Refinar é normal — mas começar bem encurta o caminho.

Contexto = qualidade

Quanto mais contexto específico (domínio, restrições, exemplos, formato esperado), melhor o resultado.

Anatomia de um Prompt Profissional — RCTFC

R

Quem o modelo deve ser nessa conversa?
C
CONTEXT
Qual é o domínio, o projeto, as restrições?
T

O que exatamente precisa ser feito?
F

Como deve ser o output? (código, UML, lista…)
C
CONSTRAINTS
O que NÃO deve aparecer no resultado?
RCTFC não é receita rígida — é checklist mental. Antes de enviar um prompt, pergunte: faltou algum dos 5 elementos?

Engenharia de Prompt · Template R.M

Prompt Profissional Completo — Imobiliária R.M

## ROLE Você é um arquiteto de software Python especialista em DDD (Domain-Driven Design) e OOP. ## CONTEXT Projeto: sistema de orçamento de aluguel para a Imobiliária R.M (Python 3.11). Domínio: 3 tipos de imóvel — Apartamento (base R$700/R$900), Casa (base R$900/R$1150), Estudio (base R$1200). Garagem: +R$300 para Apt/Casa; +R$250 +R$60/vaga extra para Estudio. Desconto: 5% em apartamento para cliente sem crianças. Taxa de contrato R$2000 em até 5x. NFRs: OOP obrigatório, manutenibilidade (SWEBOK 4.0), exportação CSV. ## TASK Gere os esqueletos das 6 classes do domínio: Imovel (abstract), Apartamento, Casa, Estudio, Contrato e Orcamento. Use ABC + @abstractmethod + @dataclass. ## FORMAT Apenas assinaturas de métodos + docstrings (1 linha por regra de negócio). Sem corpo de implementação. Blocos separados por classe. Sem imports desnecessários. ## CONSTRAINTS Não use frameworks externos. Não implemente lógica ainda. Não use @property. Não misture UI com domínio.

Arquitetura

Solução em Camadas

Camada de Domínio (Domain)

  • Imovel (abstract), Apartamento, Casa, Estudio
  • Cliente, Contrato, Orcamento
  • Regras de negócio puras — zero dependência externa

Camada de Serviço (Service)

  • OrcamentoService: orquestra o cálculo
  • ExportService: gera CSV das 12 parcelas
  • Valida entradas antes de passar ao domínio

Camada de Repositório (Repository)

  • ClienteRepository, ImovelRepository
  • Persiste e recupera dados (dict em memória por ora)
  • Isolado: troca por banco sem tocar o domínio

Camada de Interface (UI)

  • Terminal (MVP) ou Interface Web
  • Decisão pendente — depende da escolha de tecnologia
  • Nunca contém regra de negócio
UI → Service → Domain. Dependências sempre fluem para dentro.
